## Delivery rules

No release is admitted from the current protected head. Parent/head/base movement invalidates descendant acceptance evidence. Ordinary/non-force convergence must preserve valid product, test, fixture, contract and evidence deltas, but checks and reviews never transfer across moved heads. Queued, skipped, cancelled, `action_required`, COMMENTED, predecessor-head, dispatcher-only, rate-limited or source-neutral results are not GREEN. A job with no runner assignment and zero executed steps is control-plane evidence, not executed product or security evidence.

LineageWeave owns lineage/evidence/customer-master/composition/read-model behavior. It consumes released canonical-owner contracts and ACLs rather than copying contextual-orchestrator routing/admission, `.github` queue/review policy, fast-mlsirm/TEPP psychometrics, RankWeave ranking, CalendarWeave/Naruon scheduling or other owner implementations. External/model work stays outside long-lived DB transactions and explicit application locks; persistence reacquires the shortest necessary lease, revalidates state and uses idempotent/UPSERT semantics where required.

Material UI acceptance requires current-head rendered buyer evidence in addition to repository checks: normal/loading/empty/error/permission/responsive states, pointer/touch/keyboard/focus, accessible naming/status, locale expansion/font fallback and applicable performance evidence. Story/test source is evidence intent; static Storybook build alone is not interaction evidence.

A follow-up standards check found a canonical-encoding defect: Python's strict `b64decode(..., altchars=b"-_", validate=True)` still accepts standard Base64 `+`/`/` and explicit `=` padding, while RFC 7515 Base64url uses only the URL-safe alphabet with trailing padding omitted and RFC 7518 represents RSA `n` as Base64urlUInt. Causal fix `1c6c2c873052daf0f89117e290bd47bf8ab7ac9a` admits only unpadded `[A-Za-z0-9_-]+` before decoding.

The same candidate-admission boundary then exposed an RSA public-exponent gap. RFC 7518 §6.3.1 requires public RSA JWKs to carry both `n` and `e`, with `e` represented as Base64urlUInt. The predecessor selector validated `n` but counted same-`kid` candidates before validating `e`; PyJWT 2.13.0 accepts explicitly padded exponent text such as `AQAB==`, so malformed candidates could create false duplicate ambiguity. RED `ab4a5fbb059f5f0e5e0762cefc6c13958bdbed8a` plus coverage extension `8659e2ec103472c1f6820cc9447c33c12b9ccbff` exercise missing, padded, exponent-one, even-exponent and valid+malformed duplicate cases. Causal fix `912accc582128cf02a0ea9d4d9ad3ce3166e227b` factors canonical unpadded Base64urlUInt decoding and requires `e >= 3` and odd before candidate admission.

A fresh RFC 7518 terminology check found a narrower remaining canonicalization defect: Base64urlUInt is not only URL-safe and unpadded; its unsigned big-endian octet sequence **MUST use the minimum number of octets needed to represent the value**. The predecessor decoder therefore still accepted a leading-zero representation of both a full-width modulus and exponent 65537. RED `5957cf44104363cb533b8f981c4e21dc57f72b6c` adds executable non-minimal `n`, non-minimal `e`, and valid+malformed same-`kid` cases. Causal fix `e804614bd2f22ad58d2a090757c05d7a4b2072d5` rejects a leading zero on every multi-octet Base64urlUInt while preserving canonical zero (`AA`).
